# 05 复盘

## 最难的问题

### 1. 幂等键与“确认边界”的关系

最容易写错的地方不是“保存草稿”，而是“什么时候可以保存、保存后怎么确认”。

- 幂等键用 `material_id:date`，重复提交必须返回已有 `D001`，不能新增第二份；
- 但“同一天”不等于“同一时段”：M01 原要求 18:00、占用后建议 19:00，草稿的幂等键仍应是 `M01:2026-11-05`，而不是把 19:00 拼进去；
- 硬性 18:00 不能被悄悄改成 19:00；19:00 只是草稿建议，必须进入 `pending_confirmations`，由用户确认。

最后把这条边界拆成三层：

1. 提示词约束：硬性时间不改，替代时段写待确认；
2. `save_draft` 数据层：幂等键不含时段、冲突时段拒绝保存、状态只允许草稿；
3. trace：能看到模型是在看到冲突结果后才改建议，而不是预设。

这样即使用户重复提交、或模型某次想直接写 18:00，数据层也不会产生冲突草稿或第二份草稿。

### 2. 步数上限不能依赖模型措辞

第一版用“最终输出里有没有‘未完成’”判断是否触发步数上限，结果 P4 的规则阻断摘要和保存失败摘要都含“未完成”，03/05 被误判成 `incomplete`。P5 的步数测试也因为模型这次没按固定措辞输出而失败。

修复方式不是改提示词让模型“必须说未完成”，而是把判断放到工程层：

- `pre_model_hook` 记录每次模型调用时的 `remaining_steps`；
- 运行器捕获 `GraphRecursionError` 和未执行的 tool calls；
- 只有真正接近上限、且没有完成保存/阻断/失败上报时，才标记 `incomplete`；
- 中文“未完成 + 已完成部分”由 `runner_note` 统一生成，不依赖模型自由发挥。

这件事的教训是：**能用状态判断的，不要用自然语言判断**。

### 3. 真实模型的不确定性

同一份 M01 用例，P3 和 P4 的模型都按预期保存 19:00；但 P4 的 05 用例里，模型有一次把草稿保存到已占用的 18:00，工具返回 `slot_conflict`，注入失败没触发。

处理顺序：

1. 先判断是代码还是模型：保存工具正确地拒绝了冲突，说明代码没问题，是模型选择问题；
2. 优先改提示词：明确“草稿必须使用可用时段”“`slot_conflict` 后用 alternatives 重试一次”；
3. 仍不完全稳定，就把 05 的测试夹具改成“前置流程正常”（移除 18:00 占用），让失败注入成为唯一变量；
4. 不用固定分支替模型决定“必须保存 19:00”。

这条经历说明：题目允许“模型行为作为已知限制”，但不能用隐藏分支假装模型做对了。

### 4. 业务空间接口与题目默认方案不一致

题目默认 `ChatTongyi + qwen-plus`；实际业务空间只开放 OpenAI 兼容接口，原生 `/api/v1` 返回 400 `url error`。一开始我按题目默认方案写了 ChatTongyi，真实调用失败后才用原生 SDK 和兼容接口分别验证，确认是接口能力问题，不是代码问题。最后由用户确认改用 ChatOpenAI + `qwen3.8-max-0902`，并在 README、`requirements.txt`、方案文档里如实记录偏差。

## 学习收获

1. **红线要落到工具层，不只写在提示词里**：只保存草稿、拒绝冲突时段、缺字段/高风险不保存、失败不改写成功、幂等，这些都在 `save_draft`/`audit` 里有代码校验。提示词负责让模型“想到”，工具层负责“兜底”。
2. **运行记录要记录可验证的事实**：工具名、参数、结构化结果、结果摘要、模型可见说明，比“模型说它做了什么”可靠。
3. **区分代码问题和模型行为问题**：先看工具返回是否符合预期；工具对、模型选错，才是模型行为问题。代码问题直接修，模型问题先改提示词，最多两次，不用固定分支。
4. **步数上限要做双保险**：外层 `recursion_limit` 硬截断，内层 `pre_model_hook` 提醒，运行器统一生成未完成摘要。
5. **接口假设要尽早用真实调用验证**：ChatTongyi 的导入成功不代表接口可用；真实 400 让我发现了业务空间的限制。
6. **流程纪律也是工程能力**：每阶段停下、贴真实输出、逐条对照判据，比“一口气写完”更容易发现状态误判和模型不稳定。

## 下一步

如果继续迭代，我会按优先级做：

1. **拆出 `trace.py`**：把流式事件记录、摘要、落盘从 `agent.py` 拆开，降低主流程复杂度。
2. **回写业务状态**：用 LangGraph 的 state/Command 或 post-model hook 把 `task_status`、`drafts`、`pending_confirmations` 真正写入 `SchedulingState`，而不是运行后反推。
3. **步数上限中文收口**：在 CLI/runner 层把框架英文提示替换成统一的中文“未完成 + 已完成部分”，同时保留原始 `final_output` 供审计。
4. **更稳定的评测**：为六个用例加“关键事件断言”（必须先 query 再 save、save 必须在 conflict 之后等），减少单次模型波动对结论的影响。
5. **人工确认闭环**：把 `pending_confirmations` 做成可交互的确认步骤，用户确认后才把草稿转为正式排期（仍然不发布）。
6. **并发与持久化**：如果多进程/多用户，改用 SQLite 或带锁的存储，幂等键加唯一索引。
7. **支持 ChatTongyi 原路径**：如果拿到有 qwen-plus 额度的公网 key，恢复 `ChatTongyi` 接入，作为第二种模型适配。
8. **规则库扩展**：把规则从 JSON 演示数据扩展为可配置的规则文件，支持更多内容审核场景。
